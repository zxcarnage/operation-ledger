# Решения по реализации

## Транзакции и конкуренция

OperationService проверяет внешний счёт, OperationTransactions открывает короткую транзакцию записи. Разделение сделано ради Spring proxy: вызов собственного @Transactional-метода из того же объекта не откроет транзакцию. Внешний HTTP-вызов не удерживает блокировку строки или соединение пула.

Регистрация использует INSERT ON CONFLICT DO NOTHING и уникальный request_id. Предварительный SELECT сокращает обращения к сервису счетов при повторах, но не служит защитой от гонки. Защищает ограничение PostgreSQL. После INSERT запрос читает победившую запись и сравнивает бизнес-поля. Если параллельный запрос использовал другой payload, проигравший получает 409.

JPA и JdbcTemplate участвуют в одной транзакции JpaTransactionManager и используют один DataSource. JDBC нужен для PostgreSQL upsert и служебных таблиц; изменения статуса и чтение проекции остаются в JPA. После изменения статуса выполняется flush, чтобы event.version соответствовала сохранённой версии и ошибка БД произошла до записи события.

Смена статуса захватывает PESSIMISTIC_WRITE. При двух конкурирующих командах вторая увидит состояние после первой и заново проверит переход. @Version оставлен как дополнительная защита от будущих путей обновления без явной блокировки. Не следует удалять блокировку, полагаясь только на проверку enum до UPDATE.

## Доставка событий

Отправка Kafka внутри бизнес-транзакции не решает проблему двойной записи: брокер может подтвердить сообщение, а PostgreSQL — откатить операцию. Поэтому бизнес-транзакция пишет outbox. Отдельный публикатор допускает дубли и публикует eventId для дедупликации получателем. Гарантия — at-least-once.

Публикатор удерживает строку outbox, пока ждёт Kafka. Это простой компромисс для небольшой нагрузки. За одну транзакцию берётся одна запись, ожидание ограничено. При росте потока лучше CDC/Debezium или lease с ограничением параллелизма. SKIP LOCKED позволяет нескольким экземплярам работать без ожидания одной строки, но не гарантирует порядок исходящих версий одной операции. Получатель обязан учитывать version. Входящие команды нужно отправлять с ключом operationId.

Inbox защищает применение конкретного события, а не эквивалентных команд с разными eventId. Если источник повторяет одно бизнес-действие с новым идентификатором, текущая статусная машина отклонит повторный переход. Для реальных списаний понадобился бы отдельный business operation key и проводки с уникальным ограничением.

Смена счёта между REST-проверкой и коммитом возможна. Текущий контракт требует проверить активность на момент регистрации. Проверка достаточного остатка и резервирование средств требуют отдельного протокола внешнего сервиса; простой GET этого не гарантирует.

## Чтение и производительность

Open Session In View выключен. Контроллер возвращает DTO. Запрос истории явно выбирает поля, возвращает List вместо Page и не делает COUNT. В плоской модели нет связей, способных породить N+1; тест дополнительно проверяет один SQL и отсутствие загруженных сущностей. Этот проект показывает предотвращение N+1, но не содержит искусственно сломанного production-пути ради сравнения.

Индекс начинается с account_id, потому что это обязательный фильтр. Следующие поля повторяют ORDER BY. Статус в этот индекс не добавлен: текущий контракт не фильтрует историю по статусу. Индекс занимает место и замедляет запись; его польза проверяется EXPLAIN ANALYZE на реалистичном распределении.

Offset pagination проста и понятна, но глубокие страницы дорожают, а вставки между запросами могут сдвинуть содержимое страницы. Ограничен максимальный page; следующая итерация — cursor по (createdAt,id). Сортировка по двум полям решает равенство времени, но не превращает offset в snapshot.

## Что нужно обсудить на Code Review

- Где открывается транзакция и какое соединение использует JdbcTemplate?
- Сохранится ли маркер inbox после неуспешного перехода?
- Что произойдёт, если процесс упадёт после ack Kafka, но до отметки outbox?
- Сравниваются ли поля запроса при повторном ключе?
- Проверен ли конкурентный случай на PostgreSQL, а не только Mockito?
- Не ушли ли сущности или внутренние ошибки БД в HTTP-ответ?

Репозиторий не подтверждает число проведённых review, работу в конкретной команде или длительность коммерческого опыта. Он позволяет предметно проверить решения и объяснения автора.
