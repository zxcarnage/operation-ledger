# Как проверить историю операций

## Подготовка

Использовать отдельную локальную базу. Приложение сначала должно применить миграции. Затем выполнить:

~~~powershell
Get-Content perf/seed.sql -Raw | docker compose exec -T postgres psql -U ledger -d ledger -v ON_ERROR_STOP=1
Get-Content perf/explain.sql -Raw | docker compose exec -T postgres psql -U ledger -d ledger -v ON_ERROR_STOP=1
~~~

Набор содержит 200000 операций, из них 10000 у измеряемого счёта. Время и идентификаторы воспроизводимы. Данные создаются SQL напрямую, поэтому не имеют журнала и outbox: это набор для измерения чтения, его нельзя считать историей настоящих бизнес-событий.

## Измерение

1. Зафиксировать CPU/RAM, версии JDK/PostgreSQL, JVM heap, число экземпляров приложения и пул соединений.
2. Выполнить прогрев отдельным запуском k6. Не сравнивать холодный запуск с прогретым.
3. Запустить k6 run --summary-export=history-result.json perf/history.js. Сохранить p50, p95, p99, RPS и долю ошибок.
4. Повторить три раза. Параллельно снять план запроса и проверить buffers, sort и число прочитанных строк.
5. Для сравнения с baseline использовать отдельную копию БД без индекса V2 и ту же нагрузку. Не удалять индекс в общей базе.

perf/explain.sql показывает также план с отключёнными indexscan/bitmapscan внутри транзакции. Это учебный способ увидеть альтернативный план. Он не заменяет HTTP baseline и не доказывает уменьшение p95 API.

## N+1

Текущий запрос плоский: ему не нужны дополнительные сущности. historyUsesOneProjectionQuery проверяет число SQL и отсутствие загрузок Entity через Hibernate Statistics. Чтобы доказать устранение N+1 в другом проекте, нужны исходный запрос, реальные lazy-связи и сравнение SQL до/после. Добавлять лишние связи только ради красивой цифры здесь не требуется.
